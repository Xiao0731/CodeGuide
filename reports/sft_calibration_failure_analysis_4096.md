# SFT calibration 4096-token 失败分析

## 口径

- 样本：固定 40 条 dev，seed=20260728。
- Adapter 最终通过 7 条，失败 33 条。
- 4096 恢复轮只重生成了首轮撞到 2048 上限的 8 条 Adapter 回答，其余 32 条复用。
- 8 条重生成回答均自然结束，但仍未通过执行测试。
- verifier 顶层 `runtime_or_timeout` 只统计容器级错误。在单个测试用例内捕获的 `NameError`/`IndexError`/`ValueError` 仍被汇总为 `wrong_answer`，因此下表使用更细的人工根因。

## 根因汇总

## 对 8 条恢复项的单独结论

- 题意/算法错误：5 条（`124331ff26`、`1a00d261ca`、`ca005188dd`、`e9f86c2352`、`f126c597f1`）。
- I/O 解析错误：1 条（`3bd853140f`）。
- 缺少 import：1 条（`75a36187b0`）。
- 多代码块导致抽取错误：1 条（`c9bd8772b5`）。

因此，4096 恢复轮解决了“回答被截断”，但没有解决这 8 题的算法、I/O 和代码抽取错误。

## 后续工程含义

1. 该结果不应通过继续增加 `max_new_tokens` 处理。
2. 评测报告应将用例内异常从 wrong answer 中再细分，否则会低估实现和 I/O 错误。
3. 生成规范应限制最终只有一个 Python 代码块，或者让云端产物显式标记主代码块，避免示例调用覆盖真实实现。
4. 500 条校准只是管线和方向校准；大多数失败是算法泛化不足，需要全量 SFT 后在同一固定集合上重评。
